# Publish to Maven Central

The publishing namespace for this repository is `io.github.pedropietro`. Sign into [Central Portal](https://central.sonatype.com/) using the `pedropietro` GitHub account and confirm that the namespace is verified before uploading. [GitHub namespace verification](https://central.sonatype.org/register/namespace/)

The published artifact is `io.github.pedropietro:quarkus-ipfs`. The Java imports stay under `io.quarkiverse.ipfs`. The bundle contains the parent POM and the runtime, deployment, and Nabu artifacts.

## Publish a tagged release with GitHub Actions

Configure these GitHub Actions secrets for `pedropietro/quarkus-ipfs`. Use the token generated by Central Portal for `io.github.pedropietro` and a release key whose public key is available from a supported keyserver. [Portal token](https://central.sonatype.org/publish/generate-portal-token/) · [Signing keys](https://central.sonatype.org/publish/requirements/gpg/)

| Secret | Value |
| --- | --- |
| `MAVEN_CENTRAL_USERNAME` | Username generated with the Central Portal token. |
| `MAVEN_CENTRAL_PASSWORD` | Password generated with the Central Portal token. |
| `MAVEN_GPG_KEY` | ASCII-armored secret key from `gpg --armor --export-secret-keys <fingerprint>`, including the header, footer, and line breaks. |
| `MAVEN_GPG_PASSPHRASE` | Passphrase of the exported key, if protected. |

Update the Maven reactor version on `main` before tagging. For example, run `./mvnw -B versions:set -DnewVersion=0.2.0 -DgenerateBackupPoms=false` from the project root and include the POM changes in the release preparation PR.

Once the version bump is on `main`, create and push the matching tag from a checkout of that commit.

```sh
git tag -a v0.2.0 -m 'Release 0.2.0'
git push origin v0.2.0
```

The workflow accepts tags of the form `vMAJOR.MINOR.PATCH` and requires the tagged commit to be on `main` with a matching Maven version. It runs the JVM and native jobs from `Build`, signs the artifacts, and waits for Central Portal to publish them. After publication, the workflow builds an independent Quarkus application as a JAR and a Mandrel 25 Linux executable, each with its own empty Maven cache. Both run a block write and read by CID through the CDI bean. For v0.8.0 and later, the workflow also tests the published artifacts against an authenticated Kubo API behind an HTTPS proxy with the embedded node disabled. [Publication workflow](../.github/workflows/publish-central.yml)

The Build workflow retries Maven verification once after 15 seconds if Maven reports HTTP 429, 502, 503, or 504 while transferring an artifact. Test failures and persistent transfer errors fail the build. This retry runs before signing and upload.

## Recover a publication before upload

If the tag-triggered run stops before upload, select **Re-run all jobs** on that run. This rebuilds JVM and native artifacts for the same tagged commit. The workflow permits the first upload when GitHub Actions confirms that the publication job or the upload step was skipped in every prior attempt for that tag.

A completed or uncertain upload blocks another upload. If the upload step started and the deployment ID is missing, check the [Central Portal deployments](https://central.sonatype.com/publishing/deployments) for the release name. If a deployment exists, continue by ID. If GitHub history is missing or incomplete, confirm the release status in the Portal before taking any manual action. GitHub run history covers uploads done by this workflow. Check the Portal before rerunning if someone may have uploaded the bundle manually.

## Resume an existing deployment

The upload step records the deployment ID in its log, the run summary, and the `central-deployment-vMAJOR.MINOR.PATCH` artifact. The artifact contains the tag and ID.

If the wait or cache check stops after upload, open **Actions**, select **Publish to Maven Central**, then choose **Run workflow** from `main`. Enter the original tag in `release_tag` and its deployment UUID in `deployment_id`. This mode queries the existing deployment, checks the published coordinates against the tag, and reruns the empty-cache check. It skips signing and upload.

Check any deployment validation errors in the Portal using that ID. [Central Portal deployments](https://central.sonatype.com/publishing/deployments)

## Prepare the bundle manually

Use Java 21 or newer, the Maven Wrapper, and the GPG key you use for Maven Central releases. Make its public key discoverable using a key server supported by Central Portal. [Signing requirements](https://central.sonatype.org/publish/requirements/#sign-files-with-gpgpgp)

Run the build from the release checkout.

```sh
./mvnw -B clean verify
./mvnw -B -Pcentral-release -DperformRelease=true -DskipTests clean deploy
```

On PowerShell, replace `./mvnw` with `.\mvnw.cmd`.

The `central-release` profile attaches Javadoc, signs the Maven artifacts, and creates `target/central-publishing/central-bundle.zip` for manual upload. The usual Maven build also attaches the source JARs. `-DperformRelease=true` limits the release reactor to the four published modules.

## Upload and verify manually

Upload the bundle in Central Portal. Review the validation results and confirm the publication there. Once the Portal reports the deployment as published, run the functional consumer check with the published extension version and its Quarkus BOM version. Run this command from the source checkout using Bash and Python 3 on Linux, or WSL on Windows.

~~~sh
bash .github/central-consumer/verify.sh 0.9.0 4.0.0 jvm

QUARKUS_NATIVE_CONTAINER_BUILD=true \
QUARKUS_NATIVE_BUILDER_IMAGE=quay.io/quarkus/ubi10-quarkus-mandrel-builder-image:jdk-25 \
  bash .github/central-consumer/verify.sh 0.9.0 4.0.0 native
~~~

Each invocation copies the consumer into its own temporary directory and starts with an empty local Maven repository. The JVM invocation launches the packaged JAR. The native invocation requires Docker for the container build shown above and launches the resulting Linux executable. Both verify the expected CID and compare the recovered binary bytes with the original payload. In native mode for the published 0.5.0 artifacts, the script activates a compatibility profile that adds Quarkus Netty for its runtime initialization rules. The 0.6.0 extension declares this dependency itself.

For v0.8.0 and later, use the `kubo-https` scenario to verify authenticated UnixFS import and readback with the embedded node disabled. Use `kubo` to verify the v0.7.x releases over HTTP. The script starts Kubo and runs the packaged consumer on an isolated Docker network. Both invocations start with their own empty Maven repository.

~~~sh
bash .github/central-consumer/verify.sh 0.9.0 4.0.0 jvm kubo-https

QUARKUS_NATIVE_CONTAINER_BUILD=true \
QUARKUS_NATIVE_BUILDER_IMAGE=quay.io/quarkus/ubi10-quarkus-mandrel-builder-image:jdk-25 \
  bash .github/central-consumer/verify.sh 0.9.0 4.0.0 native kubo-https
~~~

The HTTPS scenario requires OpenSSL and runs a reverse proxy that exercises CA trust, hostname verification, trailers, redirects and authentication. It also imports and reads empty and 96 MiB files with a 64 MiB heap, verifying the size and SHA-256 of each file. For v0.9.0 and later, the HTTPS scenario also rotates the proxy CA in the running consumer and checks that active uploads and downloads finish.
